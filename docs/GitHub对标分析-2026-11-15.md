# ShopHub 与 GitHub 高收藏测试项目对比

核查日期：2026-11-15。用途：识别现有项目不足，供后续讨论；本文建议不代表用户已决定实施。项目进度只见[项目状态](项目状态.md)。

## 结论与比较边界

ShopHub 已有业务数据断言、独立运行环境、场景准备与清理、失败诊断及远程自动检查证据。下一步值得考虑的是核心风险测试的深度、完整链路验证和执行扩展能力。

本次没有找到足以同时满足“高收藏、同为个人电商项目、Python接口＋网页＋数据库＋性能测试”的直接同类样本。这里是本次检索范围内的结果，不代表 GitHub 上不存在。选取三个高收藏框架/平台，以及一个已归档的平台作历史参照；不能据此给个人项目排行业名次。

收藏数是 GitHub 页面显示的近似值，只作关注度线索，不证明质量。匿名 GitHub API 返回限流错误，因此未取得精确实时计数；下列数值以本次读取的页面为准。外部项目只核查仓库说明、目录及部分源码，没有部署验收。功能说明与本次亲自验证的行为需区分。

本地基线：分支 `improve-test-design`，提交 `dbe9c2c`；研究开始时工作区干净。本轮阅读实际源码与已有验收，不重新执行功能或性能测试。155条通过是11-15记录的远程历史结果，对应功能提交 `990f34f`，不是本轮新测结果。

## 选了哪些项目

| 项目与页面收藏数 | 相近之处与可参考能力 | 对比边界 |

| [SeleniumBase](https://github.com/seleniumbase/SeleniumBase)，约1.33万 | Python网页自动化；有电商示例、并行执行、浏览器选项及结果看板 | 通用自动化框架；电商只是示例，不能据收藏数判断该示例业务覆盖更深 |

| [MeterSphere](https://github.com/metersphere/metersphere)，约1.36万 | 用例、计划、缺陷、报告及组织/项目协作，说明完整测试平台的产品范围 | 团队产品，后端采用Java；版本功能存在区别，不能默认所有宣传能力均属于社区版 |

例如，ShopHub网页上的“买家下单”是被测试的商城功能；MeterSphere网页上的“选用例、执行测试、查看报告”是测试管理功能。两种网页服务于不同的人，不能把商城界面直接算作测试管理平台。

## 具体不足与影响

### 1. 业务风险覆盖仍有明确空白，建议优先讨论

有支付失败、重复支付、重复关单和最后一件竞争测试，但没有支付与关单同时发生的完整验收。[用例设计](test-cases.md)也明确完整权限与状态矩阵尚未覆盖。

例如，同一订单临近超时时，一边支付、一边关单：最终允许哪种状态？如果支付成功，库存是否仍被关单回补？父单和子单是否一致？应先确认业务规则，再控制请求先后并核对结果。

“状态矩阵”就是把起始状态与允许操作列成表，例如“待支付→发货”应拒绝，“已支付→发货”应允许；权限维度再加上买家、所属商家、其他商家。已有部分用例，缺的是系统核对与剩余组合，不是完全没测权限。

这是本地覆盖空白；本次没有证明其他框架替我们覆盖了这些商城规则，更没有复现出该竞争场景的实际缺陷。

### 2. 真实后台任务链路尚未验收，建议优先讨论

[任务定义](../server/tasks.py)和[定时配置](../server/celery_app.py)已存在；[关单用例](../api/tests/test_order.py)通过调试接口直接触发处理逻辑。[自动检查配置](../.github/workflows/ci.yml)没有启动Redis、定时调度进程与后台执行进程。

目前的证据覆盖“关单函数能处理订单”，尚未覆盖：

```text
到达扫描时间 → 调度进程发送任务 → Redis传递任务 → 后台进程执行 → 数据改变
```

例如，处理函数正确，但后台进程未启动，自动关单仍不会发生。后续可先验收真实周期关单，再考虑重复交付与进程中断恢复；不能仅打开配置就声明已验证。

依据：[Celery官方测试指南](https://docs.celeryq.dev/en/stable/userguide/testing.html)区分任务逻辑测试与后台执行测试，说明模拟执行与真实执行存在差异。官方方法是参考，不是要求现在引入新插件。

### 3. 每轮隔离已有，多用例并行仍受限

[测试准备](../conftest.py)对旧用例调用全库重置，只有标记 `owned_data` 的用例跳过；[服务](../server/main.py)中的支付故障模式属于进程共享状态。

例如，A正在检查支付失败，B重置数据库或切回支付成功，两条测试会互相影响。只创建不同账号解决不了这两类共享状态。

SeleniumBase提供并行执行入口；[pytest-xdist官方指南](https://pytest-xdist.readthedocs.io/en/stable/how-to.html)提供执行进程标识，可用于分配不同资源，但工具不会自动隔离数据库和服务状态。候选方案需要同时考虑数据库、服务、后台任务与报告文件，并实际比较顺序/并行结果与耗时。当前没有测量证据证明并行投入能节省多少时间。

### 4. 网页回归较薄，且只验收了Chromium

[网页测试](../ui/test_ui.py)有5条：买家登录、搜索、加购下单、卖家登录、开店。下单用例已有页面金额和数据库校验，这是优点；但网页付款、商家发货、买家收货和主要失败提示未形成完整回归。流水线只安装并执行Chromium。

SeleniumBase的[电商源码示例](https://github.com/seleniumbase/SeleniumBase/blob/master/examples/test_swag_labs.py)展示了购物车、结算信息和金额检查，值得参考操作与检查点的衔接，但没有证明其后台业务比ShopHub复杂。

例如，后端正确拒绝重复支付，页面却一直显示“支付中”，接口测试可能通过，网页测试才能发现用户无法继续操作。建议先补一条买卖双方网页闭环，再按明确目标浏览器选择兼容性检查；不用把接口边界用例全部搬到网页上重复跑。

依据：[Playwright官方测试执行说明](https://playwright.dev/python/docs/test-runners)支持选择多种浏览器；支持配置不等于本项目已经验证。

### 5. 性能证据仍不足以支撑完整结论

[压测脚本](../perf/locustfile.py)没有逐单校验业务响应，加购结果未校验；[历史报告](../perf/report.md)已撤回“全程零错误”等结论，保留了500用户下单档213次失败。基线版本、环境快照和锁等待等证据不完整。

例如，服务器返回HTTP 200，却生成了错误金额，脚本仍可能计为成功；收到HTTP 400却没有响应正文，就难以区分库存不足、前置数据问题或其他原因。每秒请求数也包含失败请求，不能直接当作每秒成功订单数。

建议先补业务成功标准、错误分类、数据准备核验、版本与环境记录，再选一档相同负载重复对照。需要证明锁竞争时，再采集锁等待等指标。依据：[Locust官方响应校验说明](https://docs.locust.io/en/stable/writing-a-locustfile.html#validating-responses)。本轮没有重测，不提供新性能数字。

### 6. 通用复用与平台产品能力有限，是否补取决于方向

[客户端](../api/api_client.py)已将通用请求入口和商城业务方法分文件组织，属于已有分层；但[执行器](../tools/run_tests.py)仍直接启动 `server.main:app`，场景与数据模型也围绕商城设计，尚未用第二个被测系统证明复用能力。

HttpRunner的[参数实现](https://github.com/httprunner/httprunner/blob/master/parameters.go)与[插件实现](https://github.com/httprunner/httprunner/blob/master/plugin.go)可作通用引擎参照。例如，换成设备管理系统时，请求诊断应尽量复用，而商城订单准备需要替换。只有实际做过第二个适配，才适合声称支持多业务。

与MeterSphere相比，目前缺少测试项目/用例管理、测试任务队列、网页触发执行、历史结果查询等产品能力。商城用户角色也不能当作测试平台成员权限。[MeterSphere仓库说明](https://github.com/metersphere/metersphere)可用于理解这些职责；AnotherFasterRunner仅作历史补充。

这是明确的范围差异。是否做平台，要先回答“谁通过什么页面提交哪些测试、在哪个环境执行、如何查看结果”。仅添加页面和图表不能自动补齐任务管理。若以接口自动化岗位为目标，业务和工程深化可以先做；若明确准备测试平台研发，再选最小产品范围。

### 7. 环境交付和证据展示还有可改善空间

现有本机与远程MySQL回归有证据，Docker Compose尚未实际验收。不能说没有自动部署配置，也不能说容器运行已通过。[E1验收](quality-review-2026-11-12.md)说明远程产物保留14天，本机原始报告不随克隆获得；仓库已有可获得的摘要。

例如，别人克隆后能读到155条通过摘要，但不能因此拿到本机所有原始诊断。后续可验证容器入口，并按需要保留小份脱敏示例报告或稳定证据入口。研究日期后的远程产物是否仍有效，应重新核查。

## 建议如何取舍

以下是助手建议，不是已批准计划，也不作为继续投递或面试的前置条件。

| 顺序 | 候选范围 | 完成时应能展示的证据 |
|---|---|---|
| 先选一项 | 支付/关单竞争，或真实周期关单 | 规则、测试设计、状态和库存核对、失败时的定位材料 |
| 接着按需补 | 关键权限/状态遗漏、网页买卖闭环、性能业务校验 | 每项说明解决哪种漏测，并保留真实结果 |
| 有明确收益再做 | 全套数据迁移与并行、容器执行验收 | 互不污染、清理成功、顺序/并行结果和实际耗时 |
| 方向确认后再做 | 第二业务适配，或最小测试管理页面与任务管理 | 第二使用场景，或从提交任务到查看历史报告的完整演示 |

对求职材料而言，更值得形成的例子是：“如何验证支付与关单竞争，怎样发现或排除库存回补问题”。如果没有发现真实缺陷，就说明验证结果，不为了故事编造故障。增加页面、工具名称或用例数量本身，不能推导录用优势。

## 本轮核验

- 核查本地源码、项目状态和有日期的验收材料；未把历史记录当作本轮新跑结果。
- 外部收藏数、版本变化和归档状态以仓库页面为据；能力描述以仓库说明与所链接的源码为据。
- 解释关键比较概念，并配商城例子；方法参考各工具官方文档，不把个人建议称为统一行业门槛。
- 本轮仅增加研究材料和项目状态入口；未更改程序、未启动服务、未安装依赖、未提交或推送。
