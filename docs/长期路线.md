# ShopHub · 长期路线

> 最后更新：2026-11-12。长期目标是把现有商城测试项目逐步升级为可维护、可复现、便于诊断的测试工程。当前进度只见 [项目状态](项目状态.md)。

## 状态约定

- **已确认**：用户确定方向或范围，不代表实现完成。
- **讨论中**：仍需确定边界或选择；助手推荐与候选工具保留在此状态。
- **候选**：可能有价值，尚未承诺实施；不安排默认截止日期。
- **已完成**：该阶段的验收已满足，链接实际证据；不表示此方向永远不再迭代。
- **暂缓/已替代**：说明原因及替代方案，保留历史。

## 阶段路线

| 编号 | 阶段目标 | 决策状态 | 主要交付与验收要求 | 前置条件 |
|---|---|---|---|---|
| D1 | 建立文档接手与维护机制 | 已完成；[11-12验收](superpowers/plans/2026-11-12-documentation.md#验收记录) | 入口、状态、路线、架构与决策职责明确；链接有效；按入口能找到目标、证据及下一步 | 用户11-12授权，不增加能力记录 |
| E1 | 测试工程基础升级 | 方向已确认，具体范围讨论中 | 建议优先做数据工厂、场景准备/清理、失败诊断和自动执行；以实际代表用例证明可用，详细验收随设计确认 | D1完成；确认数据与环境边界 |
| E2 | 隔离基础上的并行执行 | 候选 | 明确隔离单位，覆盖数据、服务状态、后台任务、输出文件；实测串行/并行一致性和耗时 | E1提供稳定的数据与环境管理 |
| E3 | 核心业务与真实异步链路深化 | 候选，可按风险拆小轮次 | 支付/关单竞争、真实定时调度、重复执行及历史快照等；定义规则后验证状态与副作用 | 先确认业务规则、准备手段和证据采集 |
| E4 | 可复现的性能实验 | 候选 | 版本、环境、业务成功标准、同负载对照与原始证据完整；结论与证据相符 | 功能环境与压测环境隔离；压测脚本业务校验补齐 |
| E5 | 按需求增加自动生成测试或管理界面 | 候选 | 围绕已确认问题做最小验证，再决定扩大范围 | 先证明现有工程确实需要这类能力 |

E2—E5不表示固定排期，也不要求全部实施。业务风险高时，可先从E3选一个明确场景，不必等并行执行完成。

## E1：目前讨论到哪里

用户已选择“测试工程升级”方向，并要求重新核查数据工厂等技术；还未确认具体实现设计。

| 能力 | 建议内容 | 尚需确定 |
|---|---|---|
| 数据工厂 | 生成买家、商家、店铺、商品，支持字段覆盖和对象关联 | 轻量自建或采用factory_boy；哪些对象只构造、哪些实际写入 |
| 场景准备 | 组织待支付、已支付、跨店订单等前置状态 | 哪些走真实接口；哪些允许专用数据库准备及如何检查一致性 |
| 生命周期管理 | 记录本例资源及依赖关系，失败时先取证再清理 | 清理顺序、部分准备失败、清理失败和残留资源处理 |
| 环境管理 | 独立库初始化、启动检查、执行结束清理 | 保持Compose还是增加其他工具；与现有运行方式的兼容 |
| 诊断 | 关联用例、请求、响应、服务日志和必要数据快照 | 标识传递、脱敏、保存路径、失败时采集规则 |
| 自动执行 | 单元、接口、核心网页分阶段执行并保存结果 | 首轮覆盖范围、退出码、原始证据保留方式 |
| 代表用例 | 建议购物车隔离、订单金额、最后一件库存竞争 | 迁移范围；固定种子、全表断言与全局故障开关如何兼容 |

数据工厂负责构造有规则的对象；场景准备负责获得业务状态；测试准备与清理机制负责它们何时创建和释放。例如只改订单status不能自动构成正确的“已支付订单”，还要符合明细、金额、库存等约定。

### E1设计时必须回答

1. 首轮要解决哪些现有问题，哪些延期？
2. 数据如何创建、关联、标识和清理；测试怎么取得自己的数据？
3. 改造期间旧用例如何继续运行，全局状态和全库重置如何处理？
4. 怎样验证失败诊断、资源清理和自动执行都有效？
5. 改造前后测量什么，怎样保留可信证据？不预设提速比例或覆盖率目标。

## 技术候选与查证入口

核查日期：2026-11-12。以下是可评估技术，不是已确定依赖或所有测开岗位的统一门槛。

| 方向 | 一手资料 | 对本项目的适用边界 |
|---|---|---|
| 对象数据工厂 | [factory_boy介绍](https://factoryboy.readthedocs.io/en/stable/introduction.html)、[数据库适配](https://factoryboy.readthedocs.io/en/stable/orms.html) | 当前使用PyMySQL直接执行SQL；如采用此库，需要自行适配写入，不为引库强换数据访问层 |
| 模拟字段 | [Faker](https://faker.readthedocs.io/en/master/) | 用于姓名/地址等模拟数据；关键金额和边界输入明确指定；模拟数据不冒充实测结果 |
| 创建与清理 | [pytest](https://docs.pytest.org/en/stable/how-to/fixtures.html) | 创建与对应清理配对，考虑部分准备失败；不假定工厂自动提供隔离与清理 |
| 并行执行 | [pytest-xdist](https://pytest-xdist.readthedocs.io/en/stable/how-to.html) | 进程编号可分配资源；不能自动隔离服务端全局支付开关 |
| 临时容器依赖 | [Testcontainers](https://testcontainers.com/guides/getting-started-with-testcontainers-for-python/) | 需要可用容器环境；先比较与现有Compose的收益和成本 |
| 可控依赖与故障 | [requests-mock](https://requests-mock.readthedocs.io/en/latest/overview.html)、[WireMock](https://wiremock.org/docs/simulating-faults/) | 客户端进程内替身与独立模拟服务不同；当前支付是进程内模拟逻辑 |
| 自动生成边界输入 | [Hypothesis](https://hypothesis.readthedocs.io/en/latest/)、[Schemathesis](https://schemathesis.readthedocs.io/en/stable/) | 后续小范围评估；仍需有效规则、鉴权与测试数据准备 |
| 接口协作契约 | [Pact](https://docs.pact.io/) | 当前单体项目优先级低，出现独立服务协作再评估 |

工具正式选定后，在 [决策记录](决策记录.md) 写明理由和代价，再在对应阶段设计中规定输入输出和验收。
