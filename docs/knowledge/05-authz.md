# 05 · 越权校验（授权）

> 阶段0 · 概念 5 ｜ 讲解 + 提问沉淀 ｜ 2026-08-26
> 核心术语：授权 authorization /ˌɔːθəraɪˈzeɪʃn/、鉴权 authentication /ɔːˌθentɪˈkeɪʃn/、越权 privilege escalation /ˈprɪvəlɪdʒ ˌeskəˈleɪʃn/、枚举 enumeration /ɪˌnjuːməˈreɪʃn/、IDOR（Insecure Direct Object Reference，不安全的直接对象引用）、查询级权限限定 query-level scoping

## 1. 为什么需要越权校验

前面概念 1（JWT）只解决了"你是谁"（**鉴权**）。但还有个洞：alice 登录后，如果拿到 bob 的 order_id，能不能替 bob 付钱、发货、确认收货？如果接口只验 token 有效、不验资源归属，就能——这叫**越权**。

```
请求进来（带 token）
      │
      ▼
① 鉴权 authentication ── 概念1（JWT）：验签名、验过期   "你是谁？"  失败 → 401
      ▼
② 授权 authorization ── 概念5（越权校验）：验资源是不是你的  "你有权吗？" 失败 → 404
      ▼
③ 业务逻辑（状态机 / 扣库存 / 支付）── 概念2/3/4
```

## 2. 鉴权 vs 授权（面试必考）

| | 鉴权 Authentication | 授权 Authorization |
|---|---|---|
| 回答的问题 | **你是谁？** | **你有权干什么？** |
| 手段 | JWT 验签名、验过期 | 校验资源归属（订单是不是你的） |
| 失败返回 | 401 | 404（水平越权）/ 403（垂直越权） |
| 对应概念 | 概念1 | 概念5 |

## 3. 401 vs 403 vs 404 的分工（别混）

| 状态码 | 含义 | 一句话 |
|--------|------|--------|
| 401 Unauthorized | **身份没过** | "我不认识你"（没 token / token 错 / 过期） |
| 403 Forbidden | **身份过了，权限不够** | "我认识你，但这接口你没权调用" |
| 404 Not Found | **资源不存在 OR 对你不存在** | "这东西查不到"（含"别人的数据对你不存在"） |

**关键区分（水平 vs 垂直越权决定用 403 还是 404）：**

| 场景 | 返回 | 为什么 |
|------|------|--------|
| 没登录 / token 坏 | 401 | 身份没过 |
| **水平越权**（用户间互看/互操作数据） | **404** | 别人的数据"对你不存在"，防枚举 |
| **垂直越权**（越权调更高权限的接口，如普通用户调 admin 接口） | **403** | 接口是"公开存在"的，明确拒绝"你没权限" |

一句话记：**水平越权藏起来（404），垂直越权明确拒（403）。** 本项目是水平越权，所以 404。

## 4. 防枚举：为什么"别人的订单"用 404 而不是 403

假设"非你的→403、不存在→404"，攻击者拿 id 逐个试：

- 得到 **403** → "这订单**存在**，只是不是我的"
- 得到 **404** → "这订单不存在"

**403 泄露了"订单存在"这个信息**，攻击者能枚举出系统里所有真实订单 id（**枚举攻击**，IDOR 的一种利用方式）。

正确做法：**别人的订单和"不存在的订单"返回相同的响应**，攻击者无法区分。业界用 404（把"无权"伪装成"不存在"）。

> 面试题：越权操作时，为什么"订单不属于你"返回 404 而不是 403？—— 403 会确认资源存在，助长枚举；统一 404 让攻击者分不清"不存在"和"无权"。

## 5. 核心：查询级权限限定（query-level scoping）

**越权防护的正确姿势，不是"先取到数据再拒绝"，而是"从查询源头就让别人够不到"。**

| 写法 | 问题 | 级别 |
|------|------|------|
| ❌ 先按 id 取数据，再 `if order.user != me: 403` | 数据已加载，靠 403 事后补救；可枚举；有 TOCTOU 风险 | OWASP 认为 Medium |
| ✅ 把所有权条件写进查询本身，只在自己的数据里查 | 别人的 id 根本不在搜索空间，404 是"真实的" | 最佳实践 |

**本项目代码本来就把订单按用户隔离了**（`ORDERS: dict[str, list]`，key 是用户名），但旧版 `_find_order` 却绕开隔离去 `ORDERS.values()` 全局搜，再靠 403 补救——自相矛盾。改后：

```python
def _find_order(username: str, order_id: int) -> dict:
    for order in ORDERS.get(username, []):   # 只在自己的订单列表里查
        if order["order_id"] == order_id:
            return order
    raise HTTPException(status_code=404, detail="订单不存在")
```

`ORDERS.get(username, [])` 直接取自己的订单，别人的 id 查不到 → 404。既防枚举，又更简单高效（O(自己的订单数) 而非 O(全部订单数)）。
