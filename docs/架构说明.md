# ShopHub · 当前架构说明

> 2026-11-12依据当前工作区代码整理。本文描述当前实现；未来候选能力见 [长期路线](长期路线.md)，实现进度与验证状态见 [项目状态](项目状态.md)。

## 项目边界

核心产物是围绕模拟商城的测试工程。被测系统（SUT，System Under Test）指被测试的FastAPI服务及其数据依赖。项目没有真实支付、企业上线或生产容量证明；AI协作事实不等于本人独立完成或掌握全部实现。

## 业务对象与关键机制

### 店铺库存与拆单

买家、商家是users中的角色；商家拥有店铺，同一商品可以由不同店铺销售，价格和库存属于“店铺＋商品”。跨店购物车下单后生成一个父订单、多个按店铺拆分的子订单及商品明细。

例如，店铺1和店铺2都销售键盘，购买店铺1的键盘只应扣减店铺1的对应库存。各子单分别发货/收货，父单汇总完成状态。详细表关系与状态规则分别见 [数据库结构](database-structure.md) 和 [需求草案](requirements.md)。

### 库存与事务

扣库存采用带条件的数据库更新：只有库存足够才扣减，通过受影响行数判断是否成功，并在同一事务中创建订单等数据；失败时回滚。防超卖依赖数据库条件更新与锁，不是Python线程锁。

连接池在各进程内建立；每次操作借连接并在结束后归还，事务显式提交或回滚。数据库连接池参数是当前实现细节，不直接构成性能改善结论。

并发确认不同子单收货时，当前实现先锁定相关子单及父单行，再汇总父单完成条件，避免同时确认后父单仍停留旧状态。这是具体场景的并发保护，不能推广为所有状态竞争均已验证。

### 登录与权限

登录返回签名令牌（JWT），请求携带它证明身份；密码使用带盐哈希保存，避免直接存明文。商家角色检查限制操作类型，店铺/订单归属检查限制操作对象。例如普通买家不能以商家身份修改库存，商家也不能修改其他商家的店铺。完整权限覆盖状态见用例文档，不仅凭存在检查函数就认定完整验收。

### 模拟支付与取消

支付有成功、失败、超时三种受控模式，通过服务进程内全局变量切换。它不调用银行或外部支付网关。取消采用状态条件保护，目标是重复取消不重复回补库存；这类重复操作不产生额外副作用的性质称为幂等。

请求客户端的GET/HEAD连接异常或超时可以有限重试，写请求不会自动重放；HTTP业务错误不自动重试。例如下单响应丢失时，客户端不能擅自再下单一次。

### 周期关单

定时调度器按配置扫描周期投递任务，执行器消费Redis中的消息，再调用共用的关单逻辑。直接调用调试关单接口只能验证部分业务逻辑，不能证明消息投递或真实周期调度正常。

## 当前测试的准备与判断

- 根目录测试准备函数为接口/网页用例创建独立请求客户端，但每例之前仍通过调试接口清空全库、重插固定种子，并恢复支付模式。
- `config/config.yaml`为默认配置，`TEST_ENV`选择覆盖文件，`BASE_URL`覆盖服务地址；数据库连接由环境变量提供。测试与服务必须指向同一个专用库。
- 用例按需要检查状态码、业务字段、接口回读和独立SQL查询。独立预期仍要来自业务规则，数据库回读本身不能证明规则正确。
- 网页测试以页面对象封装操作，用例检查页面和业务结果。例如购物车页负责点击购买，用例负责核对数量、金额和订单。
- 单元目录覆盖全库重置准备，不启动服务。单元替身通过与真实接口通过是不同证据。
- 当前尚未实现通用数据工厂、完整的数据归属清理或共享库多用例并行；路线图中的这些内容是待设计能力。

## 当前限制与影响

| 限制 | 实际影响 |
|---|---|
| 每例全库重置与固定编号 | 必须专用环境顺序运行；准备成本需测量，不能先宣称某个耗时比例 |
| 部分断言查询全表 | 引入独立数据后，需要改为本例资源范围，不能只删除重置步骤 |
| 支付模式为进程内全局变量 | 独立账号不能隔离此开关；功能测试保持单服务进程，多进程和并行需另行设计 |
| init_db创建shop硬编码 | 更换DB_NAME不会创建该目标库；目前无通用独立库初始化工具 |
| 请求日志主要是地址与状态码 | 复杂失败仍缺统一的用例、请求与服务日志关联 |
| 流水线主要上传网页失败产物 | 尚需设计并验证完整测试结果与服务诊断保存；已有配置不能替代执行证据 |
| 真实异步链路与竞争场景有缺口 | 不能用直接调关单的通过结果代表真实周期调度、消息交付或支付竞争正确 |
| 性能脚本缺逐单业务字段校验 | 请求速率不能直接解释为成功订单吞吐；实验结论以独立性能报告为准 |
