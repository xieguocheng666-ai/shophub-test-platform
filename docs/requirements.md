## 0. 这份文档解决什么问题

此前，测试用例的预期结果是靠"读代码反推"得到的。这有一个隐蔽风险：**代码怎么写，就被当成"应该怎样"**，万一把缺陷当成了规格，测试反而会替缺陷背书。

本文档把业务规则写成"系统应该怎样"，让每条用例的预期都有正式出处。凡是与当前实现不一致、或实现里根本没有的规则，统一列在第 9 节，不悄悄按代码写。

**诚实说明**：这个项目在开发前没有正式需求文档。本文档是事后补写的（retroactive requirements），不声称开发时就存在。只有经产品负责人逐条确认后，它才成为测试与验收的基线；确认前，正文属于"拟议需求"。

### 阅读约定

- 需求编号为 `模块-序号`，例如 `O-03` 表示下单模块第 3 条。
- 优先级：**P0** = 核心链路，错了就是资金/库存事故；**P1** = 重要；**P2** = 次要或可选。
- 每条需求的"验收标准"必须能被一条或多条测试用例核对。无法核对的表述（如"体验良好"）不进入本文档。
- 术语首次出现时给出解释；附录 A 给出"需求 → 代码 → 用例"的追溯。

## 1. 范围

### 1.1 系统定位

ShopHub 是一个用于测试练习的模拟电商后端：买家浏览店铺商品、加购、下单、模拟支付；商家按店铺发货；买家确认收货。它同时是测试框架的被测系统（SUT，System Under Test）。

平台模式：**账号与店铺分离**。一个商家账号可以开多家店铺；商品的价格和库存挂在"店铺 + 商品"上，而不是挂在商品本身上。

### 1.2 范围内

- 账号登录与 JWT 鉴权
- 商品搜索与商品详情
- 购物车（加购、查询、删除）
- 下单（按店铺拆单、原子扣库存、失败回滚）
- 模拟支付（成功 / 业务失败 / 超时三种分支）
- 子订单发货、买家确认收货、父订单聚合完成
- 店铺管理（开店、上架、查商品、改库存）
- 超时未支付订单自动取消（幂等回补库存）
- 仅调试环境可用的故障注入与数据重置

### 1.3 范围外（明确不做）

- 真实支付、银行扣款、对账、退款、售后
- 用户注册、找回密码、实名认证
- 商品下架/删除、评价、优惠券、库存预占、物流轨迹
- 高可用、分布式事务、跨服务消息最终一致性、生产级容量承诺
- 卖家后台的"我的订单/待发货列表"（当前只能凭已知子订单号操作）
- 完整的非法状态矩阵、完整权限矩阵、支付与关单并发竞争（见 9.12）

### 1.4 假设与依赖

- 数据库为 MySQL 8.0；接口层为 FastAPI；超时关单依赖 Redis + Celery。
- 测试必须使用独立测试库，不得指向任何真实数据。
- `DEBUG_MODE=1` 时开放故障注入和重置接口；生产环境必须关闭。
- 金额单位为人民币元，保留 2 位小数。

## 2. 术语表

| 术语 | 解释 | 在本项目中的例子 |
|---|---|---|
| SUT | System Under Test，被测系统。测试代码攻击的对象。 | `server/` 里的 FastAPI 服务 |
| SPU | 标准产品单元，商品的"通用信息"，只有名字，不含价格库存。 | "罗技 K845 机械键盘" |
| 店铺在售商品 | 某家店在卖某个 SPU，价格和库存挂在这一层。 | 店 1 卖键盘 299 元、库存 100 |
| 父订单 | 买家一次结算生成的整笔订单，面向买家，负责支付与聚合。 | 一次买两家店的东西，只生成一个父订单 |
| 子订单 | 按店铺拆出来的履约单元，面向商家，各自发货、各自流转。 | 上面那笔父订单拆成店 1、店 2 两条子订单 |
| 快照 | 下单那一刻把商品名、单价、店铺名复制进订单，之后商品改价改名不影响历史订单。 | 订单明细里的 299 元不会随涨价变成 399 |
| 事务 | 一组数据库操作，要么全部成功，要么全部撤销。 | 下单时扣库存、建订单、清购物车在同一事务 |
| 回滚 | 事务失败时撤销已做的修改，回到事务开始前的状态。 | 第二种商品库存不足，第一种商品的扣减也要撤销 |
| 原子性 | 一个操作不可再分：不会出现"做了一半"的中间状态。 | 扣库存只有"扣成功"和"没扣"两种结果 |
| 幂等 | 同一个操作执行多次，效果与执行一次相同。 | 同一订单取消两次，库存只回补一次 |
| 越权 | 访问了本无权访问的数据。分垂直（角色不够）和水平（同角色但数据不属于自己）。 | 买家发货 = 垂直越权；商家改别人店铺 = 水平越权 |
| 种子数据 | 初始化时插入的固定测试数据，保证每次测试从同一状态开始。 | alice、bob、seller1、seller2 四个账号 |
| JWT | JSON Web Token，登录后签发的身份令牌，接口用它识别"你是谁"。 | 请求头 `Authorization: Bearer <token>` |
| 断言 / 预期 | 断言是把实际结果与预期比较；预期是"按需求应该得到的结果"。 | 299 元买 2 件，预期金额 598 元 |

## 3. 角色与权限

| 角色 | 可以做什么 | 不可以做什么 |
|---|---|---|
| 访客（未登录） | 健康检查、搜索商品、查看商品详情 | 购物车、下单、支付、订单、店铺管理 |
| 买家 buyer | 登录、查看自己信息、管理自己购物车、下单、支付自己的订单、确认自己订单的收货 | 开店、上架、改库存、发货；操作他人购物车/订单 |
| 商家 seller | 登录；经营权限：开店、上架、查看自己店铺商品、改自己店铺库存、发自己店铺子订单；当前实现也允许加购、下单、支付、确认自己订单的收货（角色叠加） | 操作他人店铺或他人子订单；查看或操作他人购物车与订单 |
| 系统 | 周期扫描并取消超时未支付订单 | — |

权限判断有两个原则：

1. **角色从数据库实时读取**，不信任客户端 token 里写的角色。
2. **数据归属必须校验**：不仅要"你是商家"，还要"这家店是你的"；不仅要"你是买家"，还要"这个订单是你的"。

**购买权限的现状与待定项**：加购、下单、支付、确认收货目前只要求"已登录"，不校验 buyer 角色，所以 seller 账号也能购买。本文档不把"商家不能购买"写成已定规则；期望行为见 9.13，确认前按待定处理。

## 4. 业务对象与数据模型

```text
users（账号，角色 buyer/seller）
  │ 1:N（一个商家可开多店）
  ▼
stores（店铺）
  │ 1:N
  ▼
store_product（店铺在售商品：价格、库存挂这里）
  ▲
  │ 复合主键 (store_id, product_id)
  │
products（商品 SPU，只有名字）

carts（购物车：谁 + 哪家店 + 哪个商品 + 数量）
  │ 下单
  ▼
orders（父订单）──1:N──▶ sub_orders（子订单，按店铺拆）──1:N──▶ order_items（明细快照）
```

关键设计：

- `store_product` 的主键是 `(store_id, product_id)`，所以同一个 SPU 可以被多家店卖，价格库存互相独立。
- `carts` 的主键是 `(username, store_id, product_id)`，同一个人从同一家店加购同一个商品只有一行，重复加购只累加数量。
- `sub_orders.store_name` 和 `order_items.name/price` 是**快照**：订单生成后就固定，不随店铺改名或商品改价而变化。
- 父订单不存明细，明细挂在子订单下，因为履约按子订单进行。

## 5. 订单状态机

父订单（面向买家，聚合态，没有 shipped）：

```text
pending（待支付）──支付成功──▶ paid（已支付）──所有子订单 completed──▶ completed（已完成）
     │
     └──支付失败 / 超时关单──▶ canceled（已取消）
```

子订单（面向商家，独立履约）：

```text
pending ──支付成功──▶ paid ──发货──▶ shipped ──确认收货──▶ completed
     │
     └──支付失败 / 超时关单──▶ canceled
```

必须记住的三条：

1. **支付只发生一次**，在父订单层；支付成功后所有子订单同步变为 paid。
2. **发货和收货按子订单各自进行**；发货只改子订单，父订单此时仍是 paid，不会变成 shipped。
3. **父订单完成的条件是"全部子订单都 completed"**；只完成一部分时，父订单保持 paid。

## 6. 跨模块业务不变量

不变量 = 任何操作之后都必须成立的条件。测试可以拿它当通用断言。

| 编号 | 不变量 |
|---|---|
| INV-01 | 任何时刻库存不得为负。 |
| INV-02 | 父订单总额 = 所有子订单总额之和 = 所有明细（单价 × 数量）之和，精确到分。 |
| INV-03 | 同一个父订单下，每个店铺最多一条子订单。 |
| INV-04 | 父订单 pending 时，全部子订单必须也是 pending。 |
| INV-05 | 支付成功的那一瞬间，父订单为 paid，全部子订单也为 paid。 |
| INV-06 | 支付成功后子订单各自流转（paid → shipped → completed），父订单保持 paid；父订单只在全部子订单 completed 时变 completed。因此"父单 paid"不要求子单同态，只要求子单处于 paid / shipped / completed。 |
| INV-07 | 父订单 canceled 时全部子订单 canceled；父订单 completed 当且仅当全部子订单 completed。 |
| INV-08 | 订单明细中的商品名、单价、店铺名是下单时快照，不随之后的商品/店铺修改而变化。 |
| INV-09 | 购物车只包含当前用户自己的条目；下单成功后该用户购物车清空。 |

注意：INV-06 是修正后的表述。原草案写成"paid 时全部子单同态"，与"子单已发货、父单仍 paid"直接矛盾；正确的是"支付瞬间同态，之后允许子单先走"。

## 7. 功能需求

### 7.1 账号与认证

| 编号 | 需求声明（系统应该怎样） | 验收标准 | 优先级 |
|---|---|---|---|
| A-01 | 正确的用户名和密码可以登录 | 200，返回 token 和 nickname | P0 |
| A-02 | 用户不存在和密码错误都返回同一提示 | 401，"用户名或密码错误"；两种原因不区分，防止用户名枚举 | P0 |
| A-03 | 受保护接口必须携带合法 Bearer token | 缺失 → 401 "缺少 token"；伪造/签名错误/用户不存在 → 401 "token 无效"；过期 → 401 "token 已过期" | P0 |
| A-04 | token 有效期为 30 分钟 | 签发后 30 分钟内可用，超过则过期 | P1 |
| A-05 | 密码不得明文存储 | PBKDF2-HMAC-SHA256，16 字节随机盐，100000 次迭代，存为"盐hex:哈希hex" | P0 |
| A-06 | 角色只有 buyer 和 seller | 权限判断从数据库实时读取角色，不信任 token 中的声明 | P0 |
| A-07 | 合法 token 可以查询当前用户 | 200，返回 username、nickname、role | P1 |
| A-08 | 健康检查无需登录 | `GET /health` → 200，`{"status":"ok"}` | P1 |

### 7.2 商品与搜索

| 编号 | 需求声明（系统应该怎样） | 验收标准 | 优先级 |
|---|---|---|---|
| P-01 | 按商品名模糊搜索 | 关键词按"包含"匹配、大小写不敏感；空关键词返回全部；返回 items、total、page、page_size | P1 |
| P-02 | 搜索结果的一行是"某店铺在售的某商品" | 同一 SPU 在两家店卖会出现两行，价格和库存各自独立 | P1 |
| P-03 | 商品详情公开可查 | `GET /stores/{store_id}/products/{product_id}`，无需登录；不存在 → 404 "商品不存在" | P1 |
| P-04 | 搜索和分页结果稳定 | 按 store_id、product_id 升序；翻页不重复、不遗漏 | P1 |
| P-05 | 分页参数合法 | page 从 1 开始；page_size 默认 20；非法值的处理见 9.7（待确认） | P2 |

### 7.3 购物车

| 编号 | 需求声明（系统应该怎样） | 验收标准 | 优先级 |
|---|---|---|---|
| C-01 | 加购需登录，按"用户 + 店铺 + 商品"唯一 | 重复加购累加数量，不新增行 | P0 |
| C-02 | 购买数量必须大于 0 | 0 或负数 → 400 "数量必须大于 0"，不写入购物车 | P0 |
| C-03 | 只能加购该店铺在售的商品 | 不存在 → 404 "商品不存在" | P0 |
| C-04 | 累计数量不得超过当前库存 | 超出 → 400 "…库存不足（仅剩 N 件）"；失败时购物车保持原值 | P0 |
| C-05 | 加购不扣库存 | 加购前后库存不变；库存只在下单时扣 | P0 |
| C-06 | 购物车返回金额明细和总额 | 每行含店铺名、单价、数量、小计；小计 = 单价 × 数量，保留 2 位小数 | P1 |
| C-07 | 可以删除购物车中的商品 | 成功返回最新购物车；不存在 → 404 "购物车中没有该商品" | P1 |
| C-08 | 用户只能看到自己的购物车 | 不同用户的购物车互不可见、互不影响 | P0 |
| C-09 | 下单成功清空购物车，失败保留 | 成功 → 该用户购物车为空；失败 → 购物车原样保留 | P0 |

示例：键盘库存 100，购物车已有 60。追加 40 → 变成 100，成功；追加 41 → 400，购物车仍然只有 60。

### 7.4 下单

| 编号 | 需求声明（系统应该怎样） | 验收标准 | 优先级 |
|---|---|---|---|
| O-01 | 下单需登录；当前不限制 buyer 角色（见 9.13）；空购物车不能下单 | 400 "购物车为空，无法下单"；不生成任何订单 | P0 |
| O-02 | 下单是一个事务 | 读购物车 → 逐项原子扣库存 → 建父订单 → 按店铺拆子订单 → 写明细 → 清购物车；任一步失败全部回滚 | P0 |
| O-03 | 扣库存必须原子且带库存判断 | 只有 `stock >= quantity` 才扣；不足 → 400 "<商品名> 库存不足" | P0 |
| O-04 | 失败不得留下半成品 | 不得出现部分扣减、孤立的父单/子单/明细；购物车不得丢失 | P0 |
| O-05 | 金额必须可独立核算 | 父单总额 = Σ(单价 × 数量)；子单总额 = 该店明细之和；父子金额一致，精确到分 | P0 |
| O-06 | 按店铺拆单并保存快照 | 每个涉及店铺一条子订单；保存店铺名快照；明细保存商品名和单价快照 | P0 |
| O-07 | 下单成功后状态和购物车正确 | 父单、子单均为 pending；该用户购物车清空 | P0 |
| O-08 | 跨店库存独立 | 同一 SPU 在店 1 扣减不影响店 2 的库存 | P0 |
| O-09 | 以扣减时刻的实际库存为准 | 加购后商家改库存，下单时按新库存重新校验 | P0 |

示例：店 1 键盘单价 299、库存 100，买 2 件。预期父单金额 598，下单后库存 98，购物车清空；支付成功后库存仍是 98。

### 7.5 支付

| 编号 | 需求声明（系统应该怎样） | 验收标准 | 优先级 |
|---|---|---|---|
| PAY-01 | 只能支付自己的订单 | 他人订单按"不存在"处理（404），不泄露订单是否存在 | P0 |
| PAY-02 | 只有 pending 父订单可以支付 | 其他状态 → 400 "订单状态不允许支付" | P0 |
| PAY-03 | 支付成功后父子订单同步为 paid | 父单 pending→paid；全部子单 pending→paid；库存不再变化 | P0 |
| PAY-04 | 支付失败要取消订单并回补库存 | 父单和全部子单→canceled；按明细回补各店库存；明细保留、金额不变；不自动重试 | P0 |
| PAY-05 | 支付超时不能改变订单数据 | 订单保持 pending；由超时关单兜底；客户端负责处理超时 | P0 |
| PAY-06 | 已支付订单不能重复支付 | 拒绝，且订单、子单、明细、库存、购物车均不变 | P0 |
| PAY-07 | 支付是模拟的 | 不产生真实扣款、不对账；三种模式只用于测试分支 | P1 |

### 7.6 发货

| 编号 | 需求声明（系统应该怎样） | 验收标准 | 优先级 |
|---|---|---|---|
| S-01 | 只有商家能发货 | 买家调用 → 403 "需要商家权限" | P0 |
| S-02 | 只能发自己店铺的子订单 | 他人店铺 → 403 "无权操作他人店铺"；子订单不存在 → 404 | P0 |
| S-03 | 只有 paid 的子订单能发货 | 其他状态 → 400，提示当前状态不允许变为 shipped | P0 |
| S-04 | 发货只改子订单 | 子订单 paid→shipped；父订单状态不变（父订单没有 shipped） | P0 |

### 7.7 确认收货

| 编号 | 需求声明（系统应该怎样） | 验收标准 | 优先级 |
|---|---|---|---|
| CF-01 | 只能确认自己订单的收货 | 他人订单 → 403 "无权操作他人订单"；子订单不存在 → 404 | P0 |
| CF-02 | 只有 shipped 的子订单能确认 | 其他状态 → 400 | P0 |
| CF-03 | 确认后子订单完成 | 子订单 shipped→completed | P0 |
| CF-04 | 父订单只在全部子单完成后完成 | 只完成一部分时父订单保持 paid；全部完成才变 completed | P0 |
| CF-05 | 并发确认不能丢更新 | 同一父订单的多个子订单并发确认，请求都应成功，父订单最终 completed | P0 |
| CF-06 | 重复确认被拒绝且无副作用 | 已完成/已取消的子订单再次确认 → 拒绝，数据不变 | P1 |

示例：跨两家店下单，父订单有两条子订单。两家都发货后，先确认店 1：店 1 子单 completed，父订单仍是 paid；再确认店 2：父订单才 completed。
