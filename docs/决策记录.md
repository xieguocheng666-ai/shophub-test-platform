# ShopHub · 决策记录

记录会影响后续维护的重要选择，保存问题、备选方案、理由及代价。日常进度见 [项目状态](项目状态.md)，尚未确定的技术方向见 [长期路线](长期路线.md)。

每项使用固定编号；新决定替代旧决定时保留原文，并增加替代说明。记录字段为：日期、状态、问题、备选、决定、理由与代价、重评条件、关联资料。例如改用每进程独立服务和数据库，需要记录资源成本及为何账号隔离不足。

## DOC-001：采用轻量分层文档与唯一进度入口

- **日期/状态**：2026-11-12，用户确认实施。
- **问题**：项目将长期升级，新对话需要从仓库恢复目标、当前实现、进展、验证边界和下一步；原CLAUDE混合了架构、运行、进度与历史结果。
- **备选**：单一长交接文档；轻量Markdown分层；带搜索与发布流程的文档站。
- **决定**：采用轻量分层。AGENTS负责规则与导航，项目状态负责当前进度，长期路线负责阶段和决策状态，架构负责现有结构，专题文档保存细节；CLAUDE仅链接入口，README保留对外介绍和运行。用户明确不需要能力记录。
- **理由与代价**：直接沿用现有仓库，便于阅读和版本管理；需要在每轮收尾维护状态及受影响文档，避免复制动态数字和结论。路线图候选项不能自动升级为用户决定。
- **历史兼容**：保留原需求、用例、数据库和验收文档；perf/PROGRESS停止独立维护当前进度；历史计划保留日期和适用说明。
- **重评条件**：资料规模显著扩大或确有多人检索/发布需求时，再评估文档站；不预建空目录和无用途文件。
- **关联**：[协作入口](../AGENTS.md)、[本轮计划](superpowers/plans/2026-11-12-documentation.md)。

## ENG-001：E1采用轻量数据工厂与每轮独立环境

- **日期/状态**：2026-11-12，依据用户正式实施授权落地；具体技术取舍由助手提出并实施。
- **问题**：固定种子和全库重置不便表达复杂前置；失败缺请求关联；手工建库和启动易使环境不一致。
- **备选**：factory_boy、Faker配合适配层；普通Python参数对象与场景管理器；新增ORM或Testcontainers。
- **决定**：参数工厂与资源场景分开，暂不新增工厂库或ORM。账号通过专用库SQL准备，业务状态通过真实接口获得。pytest准备函数管理创建/清理；每轮执行器创建唯一库与服务，保留旧用例顺序重置。
- **理由与代价**：当前直接SQL且缺注册接口，主要难点是资源关联与清理，新增声明库不能替代这些工作。轻量实现需自行维护校验和边界；重复声明明显增多时重评成熟库。
- **归属约束**：商城按名称复用商品，工厂拒绝已存在同名商品，按明确创建编号清理，不从店铺关联推断商品所有权。当前不承诺并行创建安全。
- **诊断与执行**：每次发送生成请求标识，日志只保存路由模板等必要字段；失败记录脱敏并限制大小。执行器核对运行编号、保留真实退出码和清理状态，结果目录不覆盖。MySQL 8认证声明PyMySQL的rsa扩展。
- **重评条件**：并行执行前，先隔离全局支付开关、旧重置、后台任务与输出；确有容器环境收益再评估Testcontainers。远程CI实际运行结果另行验收。
- **依据**：[pytest准备与清理](https://docs.pytest.org/en/stable/how-to/fixtures.html)、[factory_boy](https://factoryboy.readthedocs.io/en/stable/introduction.html)、[PyMySQL认证依赖](https://pymysql.readthedocs.io/en/latest/user/installation.html)，2026-11-12核查。
- **关联**：[E1设计](superpowers/specs/2026-11-12-engineering-e1.md)、[验收](quality-review-2026-11-12.md)。
