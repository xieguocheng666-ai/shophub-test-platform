# ShopHub 性能测试报告

> 被测系统：ShopHub 电商后端（FastAPI + MySQL 8.0）
> 压测工具：Locust 2.46.6
> 优化点：DBUtils 连接池（消除「每请求新建 MySQL 连接」瓶颈）

---

## 一、摘要

对登录 / 搜索 / 下单三个核心接口做 **50–500 五档并发梯度压测**，定位到全局瓶颈是 **「每请求新建 MySQL 连接」**（建连 24.8ms 是查询 0.36ms 的 ~70 倍）。引入 **DBUtils 连接池** 后，三接口吞吐全面跃升：

| 接口 | 优化前 TPS（峰值） | 优化后 TPS（峰值） | 提升 |
|------|-------------------|-------------------|------|
| 登录 | 96.6 | 188.1 | **1.8 倍** |
| 搜索 | 183.9 | 1761.0 | **9.6 倍** |
| 下单 | 29.4 | 496.0 | **16.9 倍** |

同时量化了下单接口 `UPDATE ... WHERE stock >= qty` 原子扣库存的**行锁竞争代价**：抢同一商品（hot）相比分散商品（spread），吞吐下降 **14%–24%**，且随并发增加吞吐不升反降，印证了行锁串行化。

---

## 二、测试环境

| 项 | 值 |
|----|----|
| 被测系统 | FastAPI（`server/main.py`），4 × uvicorn worker |
| 数据库 | MySQL 8.0（`max_connections=800`，`thread_cache_size=128`） |
| 压测工具 | Locust 2.46.6，`wait_time=0`（压满） |
| 数据准备 | 1000 压测账号 + 商品库存铺到 100 万 |
| 每档时长 | 60 秒，`-u N -r N`（并发 = 每秒爬坡数） |

---

## 三、测试方案

- **接口**：`POST /login`（PBKDF2 哈希）、`GET /products`（DB 查询）、`POST /order`（事务 + 原子扣库存 + 拆单）。
- **梯度**：50 / 100 / 200 / 300 / 500 并发，五档。
- **指标**：TPS、响应时间 P50/P95/P99、错误率。
- **对照组**：
  1. **baseline**（无连接池）——每请求 `pymysql.connect()` 新建连接；
  2. **pooled**（DBUtils PooledDB）——`maxconnections=150`，复用连接；
  3. **hot**（行锁竞争专项）——所有用户抢同一商品，对比 spread 分散商品。

---

## 四、瓶颈定位（核心证据）

| 测量 | 结果 |
|------|------|
| 串行建连（connect + close） | **24.8 ms/次** |
| 复用连接查询 | **0.36 ms/次** |
| 40 线程并发建连 | 吞吐仅 **67 建连/s**（P50 514ms） |

> 结论：建连开销是查询的 ~70 倍，且并发下建连吞吐坍缩。「每请求新建连接」是全局硬瓶颈。
> 登录接口此前误判为「CPU 受限」，实测连接池后登录也提升 1.8 倍，说明它同样被建连拖累（PBKDF2 单次 39.78ms 只是第二瓶颈）。

**拐点分析**：

## 六、行锁竞争专项（`UPDATE ... WHERE stock >= qty`）

原子扣库存是「正确性优先」的设计（防超卖），代价是同一商品高并发下行锁串行化。用「抢同一商品（hot）」vs「分散 8 个商品（spread）」量化代价：

| 并发 | hot（抢同商品）TPS | spread（分散）TPS | 吞吐降幅 |
|------|-------------------|------------------|----------|
| 50 | 389.7 | 453.2 | -14% |
| 100 | 393.9 | 496.0 | -21% |
| 200 | 383.2 | 492.1 | -22% |
| 300 | 374.1 | 488.9 | -24% |
| 500 | 344.4 | 404.8 | -15% |

> 结论：行锁竞争使下单吞吐下降 **14%–24%**；hot 模式 TPS 在 100 并发见顶后随并发增加**不升反降**（500 并发跌至 344），这是行锁串行化的典型特征——并发越高，锁等待占比越大，吞吐反而下降。生产可据此决定「是否把热门商品的库存拆分到多个 store_product 行」来分散锁竞争。

## 七、优化实现（DBUtils 连接池）

```python
from dbutils.pooled_db import PooledDB

POOL = PooledDB(
    creator=pymysql,
    maxconnections=150, mincached=10, maxcached=150,
    blocking=True, ping=1, reset=True, autocommit=False,
    host=..., port=..., user=..., password=..., database=...,
    charset="utf8mb4", cursorclass=DictCursor,
)

def get_conn():
    return POOL.connection()   # conn.close() 语义变为「归还池」
```

关键点：
- `autocommit=False`：保持原 `conn.begin()/commit()/rollback()` 事务管理；
- `reset=True`：归还时自动回滚未提交事务，保证借出干净连接；
- 多 worker 下每个进程持有独立池（4 × 150 < MySQL `max_connections=800`）。

---

## 八、结论

1. 「每请求新建 MySQL 连接」是本系统**全局首要瓶颈**，连接池是性价比最高的优化（下单提升 16.9 倍）。
2. 优化后搜索/下单的 TPS 拐点在 **100 并发**，之后由事务、行锁、CPU 等次生瓶颈决定。
3. 原子扣库存的行锁竞争是「正确性优先」的合理代价，量化后吞吐损失 14%–24%，为面试讲清「防超卖 vs 性能代价」提供数据支撑。
